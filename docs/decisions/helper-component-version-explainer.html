Which crud build must an app run?

This page explains the problem with helper component versions in actions-compiler, the options that are still open, and the decision. ADR 004 records the decision. The decision matrix (helper-component-version-decision-matrix.xlsx) gives the full facts and the sources.

1. The problem

A native step, for example create, imports the crud interface. Today, actions-compiler uses that interface version as the image tag of the crud component.

create imports crud@4.0.0→ compiler→ deploys crud:4.0.0  crud 4.0.1 with the bug fix never runs

Today, one number has two functions. These two numbers must be separate:

Interface version (types)What the step can call. Only a WIT change increases it. Example: betty-blocks-types:crud@4.0.0.
Build version (component)Which code runs. Each fix increases it. Example: betty-blocks-utilities:crud@4.0.1.

Scope: a WIT change always makes a step release necessary, in each option. The options below are about a helper release without a WIT change.

2. The open options

All the options keep the step as it is. The step imports the interface version. The options differ in who decides which build serves that interface, and when an app receives a new build.

ARegistry search with an annotation

Each publish writes “I implement crud@4.0.0” on the image. The compiler searches the registry and selects the newest build that implements the imported interface.

imports crud@4.0.0→ search: 4.0.0, 4.0.1→ deploy 4.0.1 by digest
  • A fix goes to all apps at their next compile, also to old steps.

BRelease manifest

base-components publishes one list for each zone: interface version → build digest. The compiler reads the list.

imports crud@4.0.0→ manifest: crud@4.0.0 → sha256:ab12→ deploy
  • A person or CI changes the list. Rollback: set the list back.
  • After a change, all old steps in the zone receive the new build.

CA tag that moves

Each publish also puts the label types-4.0.0 on the newest build of that interface. The compiler asks for that label and resolves it to a digest.

imports crud@4.0.0→ crud:types-4.0.0 → 4.0.1→ deploy by digest
  • The smallest change of all options.
  • The same result as A: all old steps receive the build at the next compile.

DThe step declares its helper

The step release records “use crud 4.0.1”. The compiler deploys that build.

create: use crud 4.0.1→ deploy 4.0.1
  • Each step selects its build. A fix goes to a step only after a new step release.
  • If steps select different builds, the workload deploys one crud for each build.

HA lock for each app

The compiler selects the newest build as in A or C, but only one time. It writes the digest into a lock for the app. Later compiles of the app use the lock. A person or a job updates the lock: for one app, for some apps as a canary, or for all apps.

imports crud@4.0.0→ lock of app 17: crud@4.0.0 → sha256:9f01→ deploy 4.0.0  until the lock update → deploy 4.0.1
  • A save of an action does not change the helper. Old steps keep the build that operated before.
  • A fix still goes to all apps without a step release, when you decide.

4. Rejected options

E. Compose crud into the step. Each step then has its own copy of crud. We want one shared crud.
F. Shared helper for each zone. The platform must keep each old crud version live. One bad upgrade causes a failure in all apps. The data-api resource probably cannot go across workloads.
G. A bot opens the pin MR. More work: a person still merges and releases, and the team must maintain a bot across GitHub and GitLab.

Today's two approaches also stay in the matrix for comparison. The types bump causes a failure of the data-api resource, and makes a migration necessary. The pin makes a list in actions-compiler that only increases.

5. Decision

We selected option A: registry search with an annotation

Decision date: 2026-11-03. Reasons:

  1. Simple. The design is easy to understand, and the implementation is direct.
  2. Automatic. A helper release, for example a security fix, goes to the apps at their next compile. A step release is not necessary.
  3. Easy rollback. Publish a new release with the correct code and a higher version. The compiler then selects that release.

Accepted risk: old steps also receive a new helper build, and nobody tested them with it. Edge receives each release before prod. Apps that are deployed keep the old build until their next compile. For a fast fix in all apps, a recompile job is necessary. The earlier recommendation was option H (a lock for each app). The team did not select H, because H is more work, and a person must update the locks.
